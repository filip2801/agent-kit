## OpenSpec changes

We use the `openspec` CLI for spec-driven changes.

- **Always review after proposing.** When an OpenSpec propose finishes and all the artifacts
  required for apply are complete, run the `spec-review` skill on the new change and report its
  verdict and ranked findings. Skip only if the user opted out (passed `no-review` or said to skip
  it); then say so, and point them to `spec-review <change>`.
- **Don't edit the generated files.** The `openspec-*` skills and the `/opsx:*` commands are
  generated by the CLI (`generatedBy` in their frontmatter), and `openspec update` overwrites them.
  Put workflow conventions in this file instead.
- **Always commit the artifacts.** Creating or editing a change ends with a commit, without
  asking. Stage the `openspec/` paths only, leave unrelated working-tree changes alone, and say what
  the change is about rather than which files moved. For a new proposal, commit once the review's
  findings have been acted on, so the first commit holds the reviewed version. The same goes for a
  sync and an archive. During apply, don't commit per ticked checkbox; the ticks ride along when
  the run pauses or finishes.
